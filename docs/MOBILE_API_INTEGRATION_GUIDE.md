## Authentication & Security

The API uses JWT bearer tokens. Protected endpoints require an `Authorization: Bearer <token>` header.

### 1. Register a New User

```http
POST /api/v1/auth/register
Content-Type: application/json

{
  "email": "user@example.com",
  "password": "SecurePass123!",
  "full_name": "John Doe",
  "role": "patient"
}
```

Response:

```json
{
  "user_id": 1,
  "email": "user@example.com",
  "full_name": "John Doe",
  "role": "patient",
  "created_at": "2026-06-21T10:00:00Z"
}
```

### 2. Login and Get Access Token

```http
POST /api/v1/auth/login
Content-Type: application/x-www-form-urlencoded

username=user@example.com&password=SecurePass123!
```

Response:

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer"
}
```

### 3. Use the Token on Protected Endpoints

```http
Authorization: Bearer <access_token>
GET /api/v1/profile/me
```

## Password Reset Flow

The frontend currently uses the documented reset endpoints below.

### Request a Password Reset Email

```http
POST /api/v1/auth/forgot-password
Content-Type: application/json

{
  "email": "user@example.com"
}
```

Response:

```json
{
  "message": "If an account with that email address exists, a password reset email has been sent."
}
```

### Reset Password with Token

```http
POST /api/v1/auth/reset-password
Content-Type: application/json

{
  "token": "<reset-token>",
  "new_password": "NewSecurePass456!"
}
```

Response:

```json
{
  "message": "Password reset successful"
}
```

> Note: The repository's frontend code uses `/api/v1/auth/forgot-password` and `/api/v1/auth/reset-password`. The OTP endpoints shown in older docs are not the ones used by the current client contract.

## Rate Limiting

The API may return `429 Too Many Requests` if the backend enforces rate limits. Mobile clients should handle this response gracefully.

Example response:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 60
Content-Type: application/json

{
  "detail": "Too many requests. Please try again later.",
  "retry_after": 60
}
```

Recommended handling:

1. Respect the `Retry-After` header when present.
2. Disable repeated submit actions while waiting.
3. Use exponential backoff for retries.
4. Show a clear message such as “Too many attempts. Please try again shortly.”

## Mobile Sync

The current client contract uses GET requests for pull/sync status and POST for export.

### Get Sync Data

```http
GET /api/v1/mobile/sync/data
Authorization: Bearer <token>
```

### Get Sync Summary

```http
GET /api/v1/mobile/sync/summary
Authorization: Bearer <token>
```

### Get Sync Status

```http
GET /api/v1/mobile/sync/status
Authorization: Bearer <token>
```

### Export User Data

```http
POST /api/v1/mobile/sync/export
Authorization: Bearer <token>
Content-Type: application/json
```

The request body is the sync payload generated by the client.

## Diagnostic Pipeline

### Step 1: Upload an Image

```http
POST /api/v1/upload/
Authorization: Bearer <token>
Content-Type: multipart/form-data
```

Form field:

- `file`: image binary

Response:

```json
{
  "image_id": 12,
  "user_id": 3,
  "s3_url": "https://...",
  "file_name": "knee_xray_001.jpg",
  "uploaded_at": "2026-06-21T10:00:00Z"
}
```

### Step 2: Analyze the Image

```http
POST /api/v1/diagnostic/analyze
Authorization: Bearer <token>
Content-Type: application/json
```

Request body:

```json
{
  "image_id": 12,
  "pain_level": 6,
  "mobility_level": "moderate"
}
```

The `pain_level` and `mobility_level` fields are optional.

### Step 3: Fetch Reports

```http
GET /api/v1/diagnostic/reports
Authorization: Bearer <token>
```

Get a specific report:

```http
GET /api/v1/diagnostic/reports/{report_id}
Authorization: Bearer <token>
```

### Recommendations

```http
GET /api/v1/recommendation/?kl_grade=3&pain_level=6&mobility_level=moderate
Authorization: Bearer <token>
```

## Testing the API

### Using cURL

```bash
# Login
curl -X POST http://localhost:8000/api/v1/auth/login \
  -d "username=user@example.com&password=SecurePass123!"

# Get profile
TOKEN="<access_token>"
curl -X GET http://localhost:8000/api/v1/profile/me \
  -H "Authorization: Bearer $TOKEN"
```

### Using Postman

1. Set the base URL to your backend host.
2. Add an `Authorization` header with the token value.
3. Use the endpoint table below as the request reference.

### Mobile SDK Example

```python
import requests

BASE_URL = "https://kneeoa.online/api/v1"

response = requests.post(
    f"{BASE_URL}/auth/login",
    data={"username": "user@example.com", "password": "SecurePass123!"}
)

token = response.json().get("access_token")
headers = {"Authorization": f"Bearer {token}"}

profile = requests.get(f"{BASE_URL}/profile/me", headers=headers)
print(profile.json())
```

## Error Handling

The API returns standard HTTP status codes.

### 422 Validation Error

```json
{
  "detail": [
    {
      "loc": ["body", "email"],
      "msg": "value is not a valid email address",
      "type": "value_error.email"
    }
  ]
}
```

### 401 Unauthorized

```json
{
  "detail": "Could not validate credentials"
}
```

### 403 Forbidden

```json
{
  "detail": "Operation not permitted for this role"
}
```

### 404 Not Found

```json
{
  "detail": "User not found"
}
```

### 429 Too Many Requests

```json
{
  "detail": "Too many requests. Please try again later."
}
```

|--------|----------|-------------|

## Notes for Mobile Clients

- Store tokens securely (for example, in platform keystore/keychain storage).
- Handle 401 responses by prompting the user to log in again.
- Use the exact endpoint methods shown above; the frontend contract uses GET for sync pull endpoints.
- Always validate request shapes before sending them.
- If the backend responds with HTML instead of JSON, treat it as a connectivity or routing issue and surface a clear error message.
